## 2026-06-11 — Language, build, and dependencies

**Decision:** C++17, built as a static library (`libhotrod-client.a`) via CMake;
Google Test for unit tests; OpenSSL for cryptography.
**Why:** C++17 gives broad compiler support; static lib is simplest to consume;
CMake is cross-platform (Linux + Windows); OpenSSL is the standard crypto dep
and is available on both platforms (needed for SCRAM in Step 3).
**Alternatives:** C++20 (narrower compiler support at the time); header-only or
shared lib (more consumer friction).

## 2026-06-11 — Infrastructure-first porting order

**Decision:** Build the foundation (primitives → headers → auth → topology →
hashing) before any cache operations.
**Why:** Every operation then automatically inherits auth, topology-aware
failover, smart routing, and cross-platform transport. Avoids reworking
operations later. (ROADMAP v2.0.)
**Alternatives:** Operation-first (get PING/GET working end-to-end early) — would
have meant retrofitting cluster features into each op.

## 2026-06-11 — Protocol 4.0 header has 11 fields, not 8

**Decision:** Always emit the media-type and other-param-count fields for
version ≥ 0x28 / ≥ 40.
**Why:** Older test vectors show 8 fields; the real 4.0 header has 11. Omitting
fields 9–11 causes the **server to time out** with no clear error.
**Alternatives:** none — this is a protocol correctness requirement.

## 2026-06-11 — MurmurHash3 x64_32 with seed 9001

**Decision:** Use the upper 32 bits of the x64 128-bit MurmurHash3, seed 9001.
**Why:** Matches Infinispan's default exactly (byte-for-byte with the Java
`org.infinispan.commons.hash.MurmurHash3`), required for keys to route to the
same segment/owner the server expects.

## 2026-07-01 — Async-only API (breaking change, no sync wrappers)

**Decision:** All operations return `std::future`; there are **no** synchronous
convenience wrappers. `get`/`put`/`remove` return
`std::future<std::optional<ByteArray>>`; `ping` returns `std::future<void>`.
**Why:** A single async surface keeps the API small and honest about the
underlying multiplexed transport. `std::optional` gives clear "found vs. not
found" semantics without output parameters. Callers who want blocking behavior
just call `.get()`.
**Alternatives:** Keep `bool`-returning sync methods with output params
(rejected: output params are error-prone, and dual APIs double the surface);
provide backward-compatible sync wrappers (rejected while pre-1.0 — clean break
is cheaper now).

## 2026-07-01 — Temporary blocking shim during the async migration

**Decision (interim):** First ship the async *signatures* backed by a blocking
implementation that returns already-ready futures, before the real transport
existed.
**Why:** Let the API and all tests migrate once, so they wouldn't need changing
again when true async landed.
**Status:** ✅ Superseded — the real `MultiplexedConnection` replaced this shim
(see next entry). No blocking shim remains in `RemoteCache.cpp`.

## 2026 (multiplexing landing) — MultiplexedConnection design

**Decision:** One connection per server multiplexes concurrent requests over a
single socket. A dedicated read-loop thread reads responses; a
`messageId → std::promise` pending map matches responses to callers; message IDs
are generated by the connection; each operation passes a body-parser lambda to
`execute()`. Shutdown does `shutdown()` then `close()`, and `closeAllPending()`
fails any in-flight requests on error/close.
**Why:** True request pipelining (target 5–10× concurrent throughput) with one
socket per server instead of a connection per in-flight request. Connection-
generated IDs avoid cross-layer coordination. Body-parser lambdas keep response
decoding next to each operation.
**Alternatives:** Connection-per-request pool (more sockets, contention);
caller-generated message IDs (needs shared counter across layers).

## 2026-09-16 — Source hierarchy: Java client first, Kaitai schema for byte layout

**Decision:** Rank the protocol references explicitly.
1. **Java client** is authoritative for *behavior and semantics* (what each op
   does, statuses, edge cases) — study it first for every step (MANDATORY, per
   the porting workflow). Local
   `/home/rigazilla/git/infinispan/client/hotrod-client/`, public
   <https://github.com/infinispan/infinispan/tree/main/client/hotrod-client>.
2. **Kaitai schema** (`hotrod40.ksy`, protocol 4.0/4.1) is authoritative for
   *byte layout* — a precise, machine-readable cross-check of the Java client.
   Local `../hotrod-dissector/schemas/`, public
   <https://github.com/rigazilla/hotrod-dissector/tree/main/schemas>.
3. **Test vectors** are the regression check baked into unit tests.
If any two disagree, one has a bug — stop and investigate before shipping.
**Why:** The `.ksy` is an *independent* declarative encoding of the same
protocol the Java client implements imperatively, which makes it a strong
cross-check — but it describes bytes, not behavior, so it complements the Java
source rather than replacing it. Prose docs (including infinispan.org) drift.
The Step 10 metadata plan was validated against the schema (opcodes,
`entry_metadata`, `get_with_metadata_response`).
**Alternatives:** Treat the schema as the single source of truth (rejected — it
doesn't capture semantics); rely on prose protocol docs (known to drift).
